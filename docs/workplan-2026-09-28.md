## 7. ~~Cosmetic: `(9)` comm fallback~~ Investigated 2026-09-27 (code side clean)

Traced the full path: BPF `wip_state` layout matches Go's `wipState` exactly
(no offset corruption); `wip_get` has a single caller in the correct task
context; `resolveComm` prefers map-stored comm → `/proc/<pid>/comm` →
`"unknown"`. The synthetic-sample path (PID seen only in `ufm_inodes`) also
resolves via `/proc`, yielding `"unknown"` for dead PIDs — not `"9"`.
Conclusion: **no bug in our comm handling** — `"9"` is kernel-reported for
these bursters (map-captured at window-create or `/proc` at poll time).
Confirmed unknown names classify as **T2** (strictest budget). Actually
naming the process needs live WSL inspection — folded into item 1.
